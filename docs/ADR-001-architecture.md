# ADR-001: Architecture and recorded decisions

Status: accepted, 15 November 2026. Independent reconstruction from the written pack only; the original source was not read.

## Stack

| Layer | Choice | Why |
|---|---|---|
| API | Python 3.13, FastAPI, Pydantic 2 | Matches the contract style in the pack (`/api`, bearer token, `{"detail": ...}` errors) and generates OpenAPI from the real handlers. |
| Database | **PostgreSQL 16** (SQLAlchemy 2, Alembic migrations) | See "Why not MongoDB" below. |
| Office web | React 19, TypeScript, Vite, hand-written CSS design tokens | Small dependency surface; fonts are bundled, so the NAS never calls an outside font host. |
| Phone | Planned as an installable web app (PWA) sharing the same API and feature definitions | Decided in the phone stage; recorded here so office and phone stay on one contract. |
| Files | Content-addressed files on a volume with metadata rows (stage 2) | One store instead of several GridFS buckets; hash, size and MIME type recorded per file. |
| Deployment | Docker Compose: `db`, `api`, `web` (nginx serves the app and proxies `/api`) | Fits the existing Portainer/Umbrel workflow. Multi-arch base images run on the ARM NAS. |

### Why not MongoDB

The pack permits another stack if behaviour and external APIs are preserved. PostgreSQL was chosen because:

1. **Every stage can be tested against the real database in the build environment.** MongoDB could not be installed there, and tests against an imitation database would not prove persistence, uniqueness or concurrency rules.
2. The rules that matter most are relational and transactional: one immutable locked diesel week, idempotent imports by source key, frozen pay-run snapshots, optimistic revisions, foreign keys that survive archive and restore. Unique constraints and transactions enforce these in the database rather than in application code.
3. Money and rates use exact `NUMERIC` types.
4. Flexible shapes (form answers, permission matrices, provider payloads) use `JSONB`.

Cost: a later import of existing data is a mapped conversion, not a collection copy. The pack already treats migration as a separately approved step with a mapping.

## Recorded decisions

| ID | Decision | Reason |
|---|---|---|
| D-001 | Bearer tokens are opaque random values. Only a SHA-256 hash is stored, one row per session. | Gives real revocation, session history, idle timeout and "sign out everywhere" without a token-version workaround. API shape (`access_token`, `token_type`, `user`) is unchanged. |
| D-002 | `status` (`invited`/`active`/`disabled`) is the single account state. `activation_status` in responses is derived from it. | Two independent state fields can disagree. |
| D-003 | The built-in `admin` role holds every *supported* action on ordinary resources. | The observed admin matrix lacked `open` on site visitors, which reads as an omission rather than intent. |
| D-004 | Built-in `manager` starts as a copy of `supervisor`. | The pack lists `manager` as a role key but gives no default matrix. Least privilege until the owner says otherwise. |
| D-005 | `payroll` is never granted by a role or an override, only to the organisation's payroll owner (stored on the organisation; the account holder by default) and, later, named grants. | Spec section 14: an ordinary admin does not gain payroll access. Overrides the broad observed admin default. |
| D-006 | `comms_safe_mode` is never granted by a role default, only by an explicit per-user override set by an admin. | Spec section 4: a deliberately restricted capability. |
| D-007 | A non-admin can never grant access they do not hold (roles, overrides, presets, role assignment), cannot change their own role or permissions, and cannot alter an admin. | Closes privilege escalation through `users.edit`. A safeguard added by the reconstruction. |
| D-008 | `POST /api/users` creates an invited account. The baseline returned 410 and relied on Simpro import only. | Spec section 4 requires authorised invitation as well as import. It never creates a worker record. |
| D-009 | `GET /api/users` returns `{items, total, limit, offset}` instead of a bare array. | Spec section 3 requires bounded pagination with a filtered total. Intentional contract change, listed in the endpoint ledger. |
| D-010 | Custom roles are described as `resource.action` tokens. | The pack names `permission_tokens` but not their format. |
| D-011 | Applying a preset stores only the cells that differ from the person's own role; the role is not changed, and specially controlled cells are untouched. | The pack gives the response shape but not the semantics. This keeps later role changes effective. |
| D-012 | One-time links are shown once to the admin and recorded in the outbox as **held**. Nothing is emailed. | Email delivery is a later stage; a simulator must never look like a successful send. |
| D-013 | Link addresses use `PUBLIC_BASE_URL`, otherwise the admin browser's Origin. | Stops an internal API host leaking into invitation links behind a proxy. No preview-host default exists. |
| D-014 | Cross-organisation IDs answer 404, not 403. | Does not confirm that another tenant's record exists. |
| D-015 | Failed sign-ins lock the account for 5 minutes after 5 tries (423), as observed. Per-address throttling is deferred to the operations stage. | Recorded as outstanding in the ledger. |
| D-016 | An empty install is claimed through a first-run setup screen protected by `SETUP_KEY` from the server configuration. The person who completes it becomes the **account holder**. | No identity is hardcoded in the build, and a stranger who reaches a fresh install cannot claim it. |
| D-017 | The account holder must stay an active admin. Other admins cannot edit, disable, delete, demote, reset or sign out that account; only the holder can transfer it. Transfer does not move payroll ownership. | Protects the owner's account from takeover by another admin. |
| D-018 | Uploaded bytes are stored on a volume addressed by organisation and SHA-256, with a metadata row per file. Content is sniffed; a mislabelled file is refused. Missing bytes answer 410, never an empty file. | Spec section 8. Replaces the several GridFS buckets with one store. |
| D-019 | The logo route needs no session and serves only files stored as a logo. Sign-in branding is shown only when the install has a single organisation. | Branding must appear before sign-in and in reports; nothing else is reachable that way. |
| D-020 | Organisation contact fields live in one JSON column; companies keep stable ids across renames and cannot be removed while people are assigned. `slug` and `default_workspace_id` are deferred until sites exist. | Keeps foreign keys intact. |
| D-021 | Document uploads use a file-type allowlist; anything a browser could run (HTML, SVG, scripts, executables) is refused, and a PDF or image whose content does not match is refused. Only PDFs and images open inline. | Stored files must never execute in the portal's origin. |
| D-022 | Replacing a document's file creates a new revision and keeps the earlier bytes. A folder can only be deleted when empty. Re-uploading the same file to the same folder is rejected as a duplicate. | History is preserved and a retry cannot create duplicates. |
| D-023 | Managing form templates needs `forms.use` (admin and HSEQ lead in the observed defaults); deleting one needs `forms.delete`; filling in a form needs `forms.edit`; without `forms.team_view` a person sees only their own submissions. | The observed matrix gives workers `forms.edit` but not `forms.use`, so `edit` cannot be the template-management right. |
| D-024 | A template has a working draft and immutable published versions. A submission stores the version it was filled in on and renders from that snapshot. | Spec section 7: later edits must not corrupt old reports. |
| D-025 | Submitting is staged: create a draft, upload files to it, then submit. Required answers and files are checked on the server at submit; a failed check must carry a note; a submitted record is locked. A client-supplied id makes a repeated send return the first result. | Required uploads are durable before a record counts as submitted, and offline retries cannot duplicate. |
| D-026 | Answers for field ids that are not in the schema are rejected, not dropped. Picker answers are `{id, label}` references. Sites, jobs, assets and the Navixy list answer "not available yet" until their stages; vehicles may be entered by hand and are labelled as such. | No silent data loss and no invented lists. |
| D-027 | A published form with no assignment rules is open to everyone who can fill in forms. Once any rule exists, only matching roles, people or companies see it or can submit it; people who manage templates always keep access. | Avoids locking staff out by default, while making restriction explicit and previewable. |
| D-028 | PDFs are generated on request from the saved record and its version snapshot, with name, logo, address, contact and portal address from organisation settings. Photos and signatures are embedded; a lost file is stated in the PDF. | Spec section 8: the PDF must match the saved version and show unavailable attachments honestly. |
| D-029 | Reviewing a safety record needs `approve`. The built-in HSEQ lead role is given `approve` on the capture registers although the observed matrix left it off. | Spec section 6 names "HSEQ/admin review"; with the observed matrix only an admin could review. |
| D-030 | All eight safety registers share one engine. Each record stores the form schema it was captured on (the register's built-in form, or a published form template) with its answers, so register entries and form submissions render, validate and print the same way. Request bodies are `{fields: [{id, value}]}` rather than the baseline's per-register flat models. | One validation path for office, phone, API and PDF; projected forms need no translation. No legacy client depends on the old shapes in this build. |
| D-031 | A SWMS acknowledgement belongs to one version. Starting a new version creates a draft that copies answers and assignments; the old version stays in force until the new one is approved, then is marked superseded and keeps its acknowledgements. People without `swms.edit` see only approved SWMS assigned to them. | Spec section 6: an old acknowledgement must not silently point at a changed document, and an assigned admin-authored SWMS must stay visible. |
| D-032 | A submitted form whose category matches a register creates exactly one register entry (unique per submission). SSRA forms land only in the SSRA register. | Spec sections 6 and 7: no double counting; SSRA is its own destination. |
| D-033 | Hazards and incidents use open / in progress / closed. Closing needs a resolution note; edits and status changes are appended to a history that keeps the earlier answers. | Resolving must not erase the original observation. |
| D-034 | Records carry an optional site reference and free-text location until the sites register exists (stage 4). | Sites are not built yet; no invented site list. |
| D-035 | Workers can be added by hand. The baseline closed manual creation because every worker came from Simpro; the Simpro sync is stage 5, and a hand-added worker carries no source key so a later import can never overwrite it by name. | The roster has to be usable before the integration exists; imports upsert on `(source_system, source_company, source_id)` only. |
| D-036 | Worker privacy has four tiers: directory (name, position), work contact (team viewers and the worker), personal (address, emergency contact, notes: `workers.edit` or `hr_employees.view`, and the worker), protected (birth date, tax file number, USI). Protected values are encrypted with `ENCRYPTION_KEY` (Fernet), listed only as masked hints, and shown in full only through `POST /workers/{id}/reveal`, which needs `hr_employees.reveal_pii` and writes an audit entry naming the fields, never the values. Changing them needs `hr_employees.edit`. A worker cannot reveal their own protected values through the portal. | Spec section 9: masked listings, explicit reveal permission, per-access audit. `workers.reveal_pii` exists on several roles only because the baseline copied a wide default; the HR permission is the narrower, intended gate. |
| D-037 | A certificate renewal is a new row that supersedes the old one; the old row and its evidence file are kept and shown under "earlier and archived". Deleting a mistaken renewal makes the earlier certificate current again. A worker holds one current certificate per type. | "Renewal uploads update the intended worker/type and preserve previous evidence." |
| D-038 | Certificate states are valid, expiring, expired, unknown and missing. No expiry date and no "does not expire" tick means **unknown**, which never satisfies the gate and is counted separately. The register's totals are computed from the same filtered rows it lists, and the sidebar count uses the register's default population (current certificates of active workers). | "Unknown expiry is not automatically valid. The dashboard totals must match register filters." |
| D-039 | The certification gate needs the organisation switch (admin only, off by default) **and** the form's switch. It is checked on the server when a form is started and again when it is sent, against the signed-in person's own linked worker record. A login with no worker record is blocked with that reason. Required types are stored as known slugs. | Spec section 7: both switches, default off, validate slugs, expiry and worker identity on the server. |
| D-040 | The login-to-worker link is `users.worker_id` with a unique index (one login per worker). Deleting a worker unlinks the login and keeps it. Form assignment lists logins (`/forms/pickers/people`); the worker field in a form lists the worker roster. | A user and a worker are different records (spec section 3); assignment decides who can sign in and see a form. |
| D-041 | Certificate types are a per-organisation table seeded from the reference list on first use. Names and aliases resolve to a stable slug ignoring case, spaces, hyphens and underscores; a type can be retired but not deleted or re-slugged. | "Normalise known kind slugs"; old certificates must keep their type. |
| D-042 | One `site_attendance` table holds both signed-in workers and visitors without a login (`kind`). The baseline had three overlapping sign-in collections; a rebuild has no legacy rows, so there is a single intentional shape rather than a migration mapping. A partial unique index allows one open visit per person per site; visitors are deduplicated by a client reference and by name+phone while still on site. | "Repeat sign-in/out requests must not create impossible occupancy"; spec section 11 asks for an intentional mapping, not three look-alikes. |
| D-043 | The printed QR code carries a random, revocable `scan_token`, not the site id. "Issue a new code" retires every earlier sign; an inactive or deleted site's code stops working. The baseline's permanent `/sign-on/{site_id}` entry is not carried over. The address in the code comes from `PUBLIC_BASE_URL`; the site page warns when it is not set. | "Links must expire/revoke"; a permanent id in a public sign can never be withdrawn. |
| D-044 | An office sign-out closes the visit and keeps it in the log (the baseline deleted the row). Deleting a site signs out anyone still on it. Corrections to a visitor row need a reason, cannot put the sign-out before the sign-in or in the future, and store the earlier values in the audit trail. | Preserve history, actor and source; "authorised corrections". |
| D-045 | What a QR holder can read is fixed: site name, address, the organisation's display name and timezone, the sign-in questions and the visitor declaration. No ids, office notes, roster, SWMS list or other visitors. A visitor row is reachable only with its own id plus the QR token of the same site. Visitor sign-in is limited to 10 an hour per address per site. A login from another organisation is refused the staff route and told to sign in as a visitor. | "Public token endpoints are limited to the site workflow"; a worker login and a visitor session are not interchangeable. |
| D-046 | Any signed-in person may sign themself on at a site they hold the code for, whatever their role; managing sites needs `sites`, and the visitor register needs `sites_visitors` (admin and auditor in the catalogue). | Workers have no `sites` permission in the catalogue but must be able to sign on. |
| D-047 | Suppliers and contractors are one directory (`suppliers`) with an `is_contractor` flag, not two tables. `/api/contractors` is a filtered view of it. Notes, tasks and members are separate local tables; hand edits to an imported row are recorded in `locally_edited` so the Simpro import (stage 5) will not overwrite them, and the last imported values are kept apart in `source_data`. | "Do not create a second competing roster"; "an import cannot erase reviewed notes/tasks". |
| D-048 | External representatives: a user with a contractor role and `users.supplier_id` set sees and edits only that supplier (details, people, documents). Without the link they see nothing. Internal roles with `contractors.team_view` see all contractors; `suppliers.view` sees the whole directory. | The catalogue's contractor roles had no record scope to attach to; an id in a URL must not grant access. |
| D-049 | Compliance document types are per-organisation and editable, seeded with a starting set (public liability and workers compensation marked "required for contractors"). The starting set is this build's choice, not taken from the baseline, and can be changed or retired on the Renewals screen's types. Documents and certificates share the same expiry states and warning window. | The pack configures types per organisation but supplies no list; an empty list would leave the feature unusable on day one. |
| D-050 | A renewal link stores only the SHA-256 of its token; the link is shown once at creation or reissue. The public page returns only the organisation's name, who the request is for, the requested documents and their state. Uploads are restricted to the requested types, PDF or image, 15 MB. Nothing uploaded takes effect until the office accepts it per file; a rejection needs a reason, which the recipient sees on the next round. Reissuing invalidates the previous link. | "Token grants only the intended upload/view workflow… links must expire/revoke… office reviews and accepts/rejects… retain history." |
| D-051 | The renewal response reports delivery from the outbox record (`held`, or `none` when there is no recipient email), never a fixed value. | "Show whether notifications are queued, held by safe mode, sent or failed"; a simulator or placeholder must not look like a real send. |
| D-052 | An induction is a certification whose kind has `category = induction`. The inductions matrix and the certification register read the same rows; a matrix cell edits the worker's current certificate of that kind in place. "Not applicable" is a separate small table (`induction_exemptions`), so it never looks like a held certificate, and it cannot be set over a recorded completion. Retiring an induction type removes the column but keeps completions on each worker. | The baseline's cell upserted the certification document; "do not create a second competing" store; "keep archived historical types referenced by old completions". |
| D-053 | Completed training is a typed record (worker, course, provider, date, notes, evidence) rather than the baseline's sparse spreadsheet rows with dynamic columns. Editing needs `reference_library.edit` as in the baseline; a person without team access sees only their own. | A rebuild has no spreadsheet to mirror; typed fields can be validated and searched. |
| D-054 | HR documents: `hr_employees.view` lists titles, `hr_employees.edit` uploads and changes title/notes, `hr_employees.reveal_pii` opens the file, and every open writes an audit entry on the worker. The file itself is immutable. A worker cannot reach their own HR file through the portal. | Spec section 9: explicit reveal permission and per-access audit for sensitive data. |
| D-055 | Daily jobs are issued by admins only, as in the baseline (there is no `daily_jobs` resource in the permission catalogue). A partial unique index allows one active job (issued or accepted) per worker per day; issuing another needs `override`, which cancels the earlier one. "My job today" uses the organisation's timezone and never returns an earlier day's job. Accept, decline and done are open only to the worker the job was issued to. Issuing prepares an SMS in the outbox (held); the job row reports that state. The baseline's PDF and SMS job import is not built yet. | Baseline rules for the locked job shape; "phone My Work displays relevant jobs, acknowledgement/status and launch links"; nothing is ever sent by the build. |

## Security posture (applies to every stage)

- Organisation, role and record scope are checked on the server for reads, writes, downloads and exports. The menu only mirrors those checks.
- Request bodies cannot choose an organisation or act as another user; scope comes from the session.
- Passwords are hashed with Argon2id. Tokens, passwords and secrets never enter the audit log.
- Payroll stays test-only and no message, payment or lodgement is ever sent by the build; the block lives in the backend.
